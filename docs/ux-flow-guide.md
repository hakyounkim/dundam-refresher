# UX Flow 가이드 — 상태 의존성과 사용자 여정

> Claude Design 작업 시 참조용 문서.
> 시각 디자인(색·폰트·레이아웃) 이전에, 화면 간 상태 의존성·빈 상태·진입
> 경로·사용자 여정을 먼저 검토한다. 이 문서의 규칙은 화면을 새로 만들 때와
> 기존 화면을 개선할 때 모두 적용한다.

## 배경: 전형적인 실패 사례

홈(일괄 갱신기)에서 모험단을 검색해야 하는 앱에서, 드랍기록·토벌권 계산기
메뉴가 그 검색 결과에 의존한다. 그런데 메뉴로 바로 들어온 사용자에게는 빈
화면만 보이고, 왜 비어있는지도 뭘 해야 하는지도 알 수 없다. 각 화면은 정상
동작하지만 여정 관점에서는 망가진 구조다.

---

## 1. 핵심 개념: 상태 의존성 맵

모든 화면/기능에 대해 세 가지를 답한 뒤 설계를 시작한다.

1. **선행 조건** — 이 화면이 의미 있으려면 어떤 상태가 필요한가?
   (검색된 계정, 로그인, 선택된 항목, 업로드된 파일, 이전 단계 완료 등)
2. **미충족 시나리오** — 그 상태 없이 진입하면 무엇이 보이는가?
   진입 경로는 메뉴 클릭만이 아니다. 새로고침, 딥링크/URL 직접 입력,
   뒤로가기, 브라우저 재시작, 북마크, 공유받은 링크 모두 포함.
3. **충족 수단** — 그 자리에서 선행 조건을 채울 수 있는가, 아니면 다른
   화면으로 가야만 하는가?

## 2. 설계 규칙

### 2.1 빈 상태(empty state)는 1급 화면이다

선행 조건 미충족 화면은 "그냥 비어있음"이 아니라 설계 대상이다. 반드시:

- 왜 비어있는지 한 줄 설명 (예: "아직 검색된 모험단이 없어요")
- **그 자리에서 해결할 수 있는 액션**
  - 최선: 인라인 위젯 — 그 화면에 검색창을 그대로 배치
  - 차선: 명확한 이동 버튼 — "모험단 검색하러 가기"
  - 금지: 안내 문구만 있고 액션이 없는 것, 또는 아무것도 없는 빈 화면
- 가능하면 화면 골격(테이블 헤더, 카드 자리 등)을 보여줘서 "여기서 뭘 볼
  수 있는지"를 예고한다

### 2.2 공유 컨텍스트: 지속·표시·변경

여러 화면이 공유하는 상태(선택된 계정, 모험단, 프로젝트, 기간 등)는:

- **지속**: 메모리에만 두지 말고 URL 파라미터 또는 localStorage에 저장.
  새로고침·딥링크·재방문에도 유지된다. 공유 가능해야 하면 URL, 개인
  기억이면 localStorage (병행 가능)
- **표시**: 현재 컨텍스트를 헤더 등 모든 화면에서 보이는 위치에 노출
  (예: "현재 모험단: 꿀앤똑" 배지). 사용자가 "지금 뭘 기준으로 보고
  있는지"를 화면마다 추측하게 하지 않는다
- **변경**: 홈으로 돌아가지 않아도 그 배지를 눌러 어디서든 변경 가능

### 2.3 진입점 독립성

모든 화면은 URL로 직접 진입해도 성립해야 한다. SPA라도 라우트별로 "이
URL만 받았을 때 상태를 복원할 수 있는가"를 확인한다. 복원 불가한 상태에
의존한다면 2.1의 빈 상태 규칙으로 처리한다.

### 2.4 첫 방문자 경로

아무 데이터도 없는 신규 사용자가 각 메뉴를 눌렀을 때의 경험을 확인한다.
홈이 아닌 메뉴가 사실상 첫 화면이 될 수 있다 (북마크, 공유 링크).

### 2.5 파괴적/장시간 동작의 여정

삭제·초기화·일괄 갱신 같은 동작은 확인 → 진행 표시 → 결과/실패 알림 →
(가능하면) 되돌리기까지가 한 세트다. 버튼 하나 달고 끝내지 않는다.

## 3. 리뷰(감지) 절차

기존 앱을 검토할 때는 시나리오 워크스루로 진행한다.

1. 화면/메뉴 목록을 뽑고 각각의 선행 조건을 표로 정리 (상태 의존성 맵)
2. 신규 사용자 시나리오: 데이터 0인 상태에서 모든 메뉴를 하나씩 진입
3. 복귀 사용자 시나리오: 어제 쓰던 사용자가 새로고침/재방문했을 때
   컨텍스트가 살아있는가
4. 딥링크 시나리오: 각 라우트 URL을 새 탭에 직접 붙여넣기
5. 발견한 문제는 "화면 X는 상태 Y에 의존하는데, 경로 Z로 진입 시 대응
   없음" 형식으로 기록하고, 위 규칙 중 어느 것으로 고칠지 명시

심각도 구분: 기능이 무의미해지는 것(빈 화면, 데이터 유실)을 먼저,
불편한 것(이동 강요, 컨텍스트 비표시)을 다음으로 다룬다.

## 4. 신규 개발 시 적용 순서

- 첫 화면 설계 시점에 화면 목록과 상태 의존성 맵부터 그린다
- 공유 상태가 하나라도 있으면 컨텍스트 표시 UI(헤더 배지 등)를 처음부터
  레이아웃에 포함시킨다 — 나중에 끼워 넣으면 레이아웃을 다시 짜게 된다
- 라우팅 설계 시 공유 상태를 URL에 태울지 localStorage로 할지 먼저 결정
- 각 화면 구현 순서: **빈 상태 → 로딩 상태 → 정상 상태**. 빈 상태를
  마지막으로 미루면 대부분 생략된다

## 5. 적용 대상: dundam-refresher (dundam-refresher.vercel.app)

### 현재 구조와 문제

- 홈 = 일괄 갱신기. 여기서 모험단을 검색한다
- 드랍기록, 토벌권 계산기 메뉴는 홈에서 검색한 모험단에 의존한다
- 문제: 모험단을 검색하지 않고 다른 메뉴에 진입하면 의미 있는 것이 없다.
  상태 의존성 맵으로 표현하면 — "드랍기록/계산기 화면은 '검색된 모험단'
  상태에 의존하는데, 메뉴 직접 진입·새로고침·딥링크 경로에서 대응 없음"

### 개선 처방 (우선순위 순)

1. **인라인 검색** — 드랍기록·토벌권 계산기의 빈 상태에 모험단 검색창을
   그대로 배치한다. 홈에 다녀올 필요 자체를 없앤다 (규칙 2.1)
2. **컨텍스트 지속** — 검색된 모험단을 localStorage에 저장하고 URL에도
   반영한다 (예: `?adventure=꿀앤똑`). 새로고침·공유·재방문 대응 (규칙 2.2, 2.3)
3. **헤더 배지** — 모든 화면 헤더에 "현재 모험단: 꿀앤똑" 배지를 노출하고,
   클릭 시 변경 팝오버를 연다 (규칙 2.2)
4. **빈 상태 골격** — 모험단 미설정 상태로 메뉴 진입 시에도 테이블 헤더 등
   화면 골격은 보여줘서 이 화면에서 뭘 볼 수 있는지 예고한다 (규칙 2.1)

### 시각 디자인 전제 (기존 컨벤션 유지)

- 토스/당근 계열의 깔끔한 미감
- 라이트/다크 듀얼 테마 — 시스템 설정 추종 + 수동 토글
- 모바일 퍼스트
